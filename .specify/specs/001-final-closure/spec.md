# Feature Specification: 终局闭环 —— 上一轮改进指南的未闭环项补齐与可验证交付

- **Spec ID**: 001-final-closure
- **状态**: draft
- **日期**: 2026-10-12
- **适用仓库**: `mailcow-dockerized-Max`（生产环境 `mail.pony-it.com` 在用）

---

## 1. Overview / Context

上一轮改进指南（`docs/计划指南/下一步改进指南.md`）把一批问题登记为待修：P0-1..P0-4、P1-1..P1-4、P2-1..P2-5，以及验收标准 A1..A10。

风险在于：**该项目历史上多次出现「文档声称已修，后续实测推翻」的情况**（文档自身在 §P1-1、附录 A 里记录过至少两次自我修正）。所以本轮的真正问题不是"还剩什么没做"，而是：

> 指南登记的每一项，**今天在代码里到底是「真闭环」还是「纸面闭环」**？

并把确认为未闭环的部分补到**可被独立复核**的程度。

### 使用者

- **主要**：项目维护者（单人全栈，既改代码也做验收）
- **间接**：生产环境里的邮件管理员（通过 Web 后台使用域名健康、总览、养号等功能）
- **间接**：邮件链路的"调用方"——出站 SMTP 路由，任何错误都会直接表现为发信失败

### 不在本轮范围

- 需要用户本人授权的第三方接入（Google Postmaster OAuth、Mailtrap 公司信息、serv00 凭据）
- 需要生产服务器访问权的操作（本机无该主机 SSH 凭据）
- 上游 mailcow 原样代码的风格性重构

## 2. User Scenarios

| # | 场景 | 使用者 | 期望结果 |
|---|------|--------|----------|
| S1 | 改完域名健康相关代码，想确认判定逻辑没坏 | 维护者 | 一条命令给出确定性结论，**不需要**起 PHP 栈、不需要数据库 |
| S2 | 把某个邮箱绑到一台 `:465` 中继，而该域的中继是普通端口 | 维护者 | 出站 TLS 方式与**实际选中的主机**匹配；不会"对 465 发明文"，也不会"对普通端口启用隐式 TLS" |
| S3 | 把界面切到英文/繁体 | 邮件管理员 | 域名健康入口与弹窗文案跟着语言变，不出现硬编码或空白 |
| S4 | 隔一段时间回来接手 | 维护者 / 下一个 AI 会话 | 按仓库文档就能知道：哪些验证做过、改动后要重跑什么、要重启什么 |
| S5 | 评审这次改动 | 独立评审者 | 一份报告里能看到：改了什么、证据是什么、哪些未验证、为什么 |

## 3. Functional Requirements

> 每条都以「可被外部观察到」的方式陈述；括号内为**验收判据**。

- **FR-1** 指南中登记的每一项，都必须给出「真闭环 / 部分闭环 / 未闭环 / 不适用」的判定。
  （验收判据：判定表逐项存在；每项判定都附 file:line 或命令输出；**不采信文档的自我宣称**。）

- **FR-2** 域名健康的判定逻辑，必须能在**无数据库、无 redis、无网络**的环境里被执行并断言。
  （验收判据：在只有 PHP 解释器的环境里运行测试入口，退出码 0。）

- **FR-3** 出站 transport 的 TLS 模式，必须由**实际被选中的下一跳主机**决定；邮箱级与域级中继必须用同一套口径。
  （验收判据：对「邮箱级 `:465` / 域级非 465」与「邮箱级非 465 / 域级 `:465`」两种配置，映射结果都正确；且现有生产配置的映射结果前后完全一致。）

- **FR-4** 域名健康功能的入口与弹窗文案，必须来自语言包。
  （验收判据：对相关文件做全量中文字符扫描返回空；三个语言包对应键齐全。）

- **FR-5** 关键测试必须**在 CI 中被真实调用**，而不是只存在于仓库里。
  （验收判据：CI 配置中存在调用；任一测试失败会让 CI 失败。）

- **FR-6** 指南中确认为未闭环的项，必须补齐，或明确标注阻塞原因与缺失条件。
  （验收判据：「未闭环」项数量为 0，或每一项都有明确的阻塞说明。）

- **FR-7** 必须输出一份**可独立打开**的变更报告，含上下文、动机、改动、以及底部测验。
  （验收判据：单文件 HTML，离线可读；测验必须全部答对才算通过。）

- **FR-8** 必须有**独立于实现者**的审查结论，且审查方不得直接改代码。
  （验收判据：审查报告存在；发现的问题有处置记录；修复后有复验记录。）

- **FR-9** 仓库文档（文档索引、工作流状态）必须与真实状态一致。
  （验收判据：文档点名的文件都存在；索引链接可达；状态表与代码事实相符。）

- **FR-10** 必须沉淀「下次新增功能」的可复用工作流与技能，且该技能强制要求：先读记忆与文档 → 判断是否过时 → 再读真实代码 → 才动手。
  （验收判据：技能文件存在，且其描述中明确包含上述顺序与验收要求。）

## 4. Success Criteria

| # | 判据（用户视角） |
|---|------------------|
| SC-1 | 维护者一条命令就能得到域名健康判定逻辑的通过/失败结论；该命令在**没有数据库和缓存的机器上**同样跑得通 |
| SC-2 | 两种"邮箱级与域级中继端口不一致"的配置下出站行为都正确；且**生产现有配置的映射结果前后一模一样**（零回归） |
| SC-3 | 三种界面语言下入口文案都正确；相关文件的中文扫描结果为 0 处 |
| SC-4 | 关键测试在 CI 中被真实调用；测试挂掉 CI 就红 |
| SC-5 | 指南每一项都有判定与证据；「未闭环」为 0 或每项都有阻塞说明 |
| SC-6 | 变更报告能离线打开，底部测验必须全部答对 |
| SC-7 | 审查由非实现者完成，发现的问题有处置与复验记录 |
| SC-8 | 新技能能让下一个会话直接判断"文档过没过时"，而不是重新摸索 |

## 5. Edge Cases

| 边界 | 期望行为 |
|------|----------|
| 没有 relayhost | 走默认 `smtp:`，不影响直发 |
| 域级与邮箱级中继同时存在且不同 | 以**邮箱级优先**（与 mailcow 原生 nexthop 口径一致） |
| 两者都不是 465 | 不用隐式 TLS 连接器 |
| hostname 不含端口 | 不误判为 465 |
| 语言包缺 key | 回退英文，**不得显示空白或 `undefined`** |
| CI 无 PHP 栈 / 无 redis / 无 DB / 无网络 | 测试仍可执行（这是 FR-2 的存在理由） |
| 生产服务器不可达 | 仍能交付，并在报告中如实标注"未验证" |

## 6. Assumptions & Constraints

1. **不引入新依赖**：项目无 composer/npm，测试只能用 PHP/Python/Node 标准能力与自建轻量断言。
2. **不动上游表结构**：`relayhosts` 表没有 `port`/`description` 列，因此"按服务商打标"的方案不可行（需改表且改 `db_version`，风险大于收益）。
3. **不修改 `LICENSE`**（GPLv3）。
4. **生产部署由运维方执行**：本机没有 `15.204.205.80` 的 SSH 凭据，本轮只能交付"可执行的部署/回滚步骤 + 本地等效验证"。
5. **真实 465 中继端到端投递受外部条件限制**（Cloudflare 侧限流与会话可用性），此项若无法完成必须显式标注为未验证。
6. 推送目标为 `https://github.com/lza6/mailcow-dockerized-Max` 的 `main` 分支；远端与本地 `master` **无共同祖先**，只能快进，**绝不 force push**。
