## 二、表结构与索引分析

### 2.1 表定义机制（`data/web/inc/init_db.inc.php`，1626 行）

所有表在 PHP 数组 `$tables` 中声明（`init_db.inc.php:58` 起），由 `init_db_schema()` 在启动时与数据库实际结构做**双向同步**：

- `init_db.inc.php:1255-1298` —— 遍历声明的 `keys`，缺则 `ADD`，多则 `DROP`；
- `init_db.inc.php:1299-1306` —— **删除数据库中存在但声明中不存在的列**；
- `init_db.inc.php:1308-1333` —— **删除数据库中「不属于声明」的所有非主键索引**。

> **这是本报告最重要的一条架构约束：**
> 任何手工执行 `ALTER TABLE ... ADD INDEX` 都会在下次 `init_db_schema()` 运行时被**自动删除**。索引必须写进 `data/web/inc/init_db.inc.php` 的 `"keys"` 数组才会持久化。
> 因此第五节所有索引建议，落地方式都是「改 `init_db.inc.php` 并提升 `$db_version`」，而非直接连库执行 DDL。

单条表声明形如：

```php
"mailbox" => array(
  "cols" => array( ... ),
  "keys" => array(
    "primary" => array("" => array("username")),
    "key"     => array("domain" => array("domain"), "kind" => array("kind")),
  ),
  "attr" => "ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 ROW_FORMAT=DYNAMIC"
),
```

字段类型选型整体合理：`id` 用 `INT AUTO_INCREMENT`、状态位用 `TINYINT(1)`、可变结构用 `JSON`、时间用 `DATETIME(0)`。

### 2.3 发现的问题（附证据）

#### 【结构问题 A】`sender_acl` 无二级索引 → 出站发信 ACL 全表扫描

`data/conf/postfix/sql/mysql_virtual_sender_acl.cf` 是**每次出站发信都会执行**的查询，其 UNION 分支：

```sql
SELECT logged_in_as FROM sender_acl
  WHERE send_as='@%d' OR send_as='%s' OR send_as='*'
     OR send_as IN (SELECT CONCAT('@',target_domain) FROM alias_domain WHERE alias_domain = '%d')
     OR send_as IN (SELECT CONCAT('%u','@',target_domain) FROM alias_domain WHERE alias_domain = '%d')
  AND logged_in_as NOT IN (SELECT goto FROM alias WHERE address='%s')
```

实测 EXPLAIN：

```
id  select_type  table       type  possible_keys  key   rows  Extra
1   PRIMARY      alias       ALL   NULL           NULL  16
2   UNION        sender_acl  ALL   NULL           NULL  1     Using where   ← 全表扫描
```

`possible_keys = NULL` 证明优化器**没有任何索引可用**。当前 `sender_acl` 为 0 行故无感，但只要启用「按域名 send-as 授权」（多域名场景必然用到），该查询随表增大线性劣化。

#### 【结构问题 B】`resend_domains` 缺 `account_id` 索引 → 统计查询 filesort + 临时表

`functions.resend_pool.inc.php:123`、`:487` 的统计查询：

```sql
SELECT account_id, COUNT(*) AS c FROM resend_domains WHERE active = 1 GROUP BY account_id
```

实测 EXPLAIN：

```
table           type  possible_keys  key   Extra
resend_domains  ALL   NULL           NULL  Using where; Using temporary; Using filesort
```

`resend_pool_accounts()` / `resend_pool_auto_assign()` 都会调用它。当前 0 行无感。

#### 【结构问题 C】`domain.relayhost` 为 `VARCHAR(255)` 却存数字 ID，且无索引

```php
"relayhost" => "VARCHAR(255) NOT NULL DEFAULT '0'",   // init_db.inc.php:305
```

实际数据为 `'0'` / `'4'` 等字符串。postfix 的 `mysql_sender_dependent_default_transport_maps.cf` 与 `mysql_sasl_passwd_maps_sender_dependent.cf` 通过 `domain.relayhost = relayhosts.id` 关联，即 **VARCHAR 与 INT 跨类型比较**。当前能工作，因为 `relayhosts` 只有 4 行、优化器选择全表扫描驱动（见 3.2），类型转换的代价被掩盖。这是**上游 mailcow 的既有设计**，改动会破坏上游兼容性，见第七节。

## 三、热点查询分析

### 3.1 postfix 的 SQL 映射（每次收/发信都执行）

服务器 `data/conf/postfix/sql/` 下共 20 个 `.cf` 文件，均为「Autogenerated by mailcow」。核心两类：

#### (a) 发信中继选择（有中继绑定时最重的查询）

`mysql_sender_dependent_default_transport_maps.cf`（发信时确定走哪个 relayhost）—— 完整语句见附录 3.1；简化结构：

```sql
SELECT COALESCE(
  (SELECT hostname FROM relayhosts
     LEFT JOIN mailbox ON JSON_UNQUOTE(JSON_VALUE(mailbox.attributes,'$.relayhost')) = relayhosts.id
     WHERE relayhosts.active=1 AND mailbox.username IN (...)),
  (SELECT hostname FROM relayhosts
     LEFT JOIN domain ON domain.relayhost = relayhosts.id
     WHERE relayhosts.active=1 AND domain.domain = '%d')
)
```

实测 EXPLAIN：

```
id  select_type  table       type  possible_keys  key   rows  Extra
3   SUBQUERY     alias       ALL   address        NULL  16    Using where
8   SUBQUERY     relayhosts  ALL   NULL           NULL  4     Using where
8   SUBQUERY     domain      ALL   NULL           NULL  16    Using where; Using join buffer (flat, BNL join)
```

`mysql_sasl_passwd_maps_sender_dependent.cf`（取中继认证凭据）同样：

```
3   SUBQUERY     relayhosts  ALL   NULL  NULL  4   Using where
3   SUBQUERY     domain      ALL   NULL  NULL  16  Using where; Using join buffer (flat, BNL join)
```

#### 解读

1. **`domain` 表在 `relayhosts` JOIN 中走全表扫描 + BNL join。** 原因是双重：`domain.relayhost`（VARCHAR）与 `relayhosts.id`（INT）类型不匹配，且 `relayhost` 无索引。
2. **在当前规模下这完全不是问题**：`relayhosts` 4 行 × `domain` 16 行 = 64 行组合，Postfix 又有 10 秒 TTL 缓存（`postmap` 结果缓存于进程内存）。实测单次发信无感知。
3. **`JSON_VALUE(mailbox.attributes,'$.relayhost')` 无法走索引** —— 但该分支仅当邮件走「邮箱级中继」时才命中，本部署未使用邮箱级中继。
4. **实质结论：这是上游 mailcow 的设计性权衡**（用 JSON 换取灵活性、用全表扫描换取对 relayhosts 做增删的零迁移成本），**不属于本仓库引入的缺陷**，且在上游架构下无更优解。见第七节。

#### (b) 常规收信查询（全部走索引，健康）

| 查询 | 实测 EXPLAIN |
|------|-------------|
| `mysql_virtual_mailbox_maps.cf`：`SELECT ... FROM mailbox WHERE username='%s'` | `type=const, key=PRIMARY, rows=1` ✅ |
| `mysql_virtual_alias_maps.cf`：`SELECT goto FROM alias WHERE address='%s'` | `type=const, key=address, rows=1` ✅ |
| `mysql_virtual_domains_maps.cf`：`SELECT ... FROM domain WHERE domain='%s'` | `type=const, key=PRIMARY, rows=1` ✅ |
| `mysql_virtual_relay_domain_maps.cf`：同 domain 主键 | `Impossible WHERE ... const tables`（等价常量折叠）✅ |

**收信主路径的索引覆盖是健康的。**

### 3.2 PHP 中的查询模式

#### N+1 模式

- **整体健康。** 中继批量操作（`resend_pool_auto_assign`）内部对每个域名调用 `resend_pool_assign`，属于外部 API 调用场景（非纯 DB），且每条都有独立事务语义，不构成典型 N+1 缺陷。
- `functions.resend_pool.inc.php:118-126` 用**两条聚合查询**（账号列表 + 每账号域名计数）替代逐账号查询，是**正确的反 N+1 写法**，值得肯定。

#### `SELECT *`

全库 46 处（`functions.inc.php` 13、`functions.mailbox.inc.php` 8、`resend_pool` 3 …）。这是**上游 mailcow 的普遍风格**，非本仓库引入。在 mailcow 的「宽表 + 强缓存」场景下，`SELECT *` 的额外列代价可忽略，**不建议为此做大规模重构**（见第七节）。

#### SQL 字符串拼接 / 注入面（静态确认）

对 `data/web/inc/**` 全量正则扫描动态 SQL：

```
pdo->query("...$var...")  → 仅 4 处命中
```

逐条核查：

| 位置 | 拼接内容 | 来源 | 结论 |
|------|---------|------|------|
| `functions.mailbox.inc.php:3622` | `UPDATE $table SET $column = :v` | `$table`/`$column` 来自**函数内硬编码数组**（`:3605-3619`） | 非注入 ✅ |
| `init_db.inc.php:1261-1367` | `SHOW KEYS FROM \`$table\`` 等 DDL 拼接 | `$table`/`$key` 来自**本文件静态声明** | 非注入 ✅ |

| `lib/ssp.class.php`（DataTables 服务端处理） | `ORDER BY \`$tableAS\`.\`$db\` $dir`、`LIKE $binding` | `$db` 列名来自服务端 `$columns` 定义；`$dir` 限定 `asc`/`desc`；搜索值走 binding | 非注入 ✅ |

### 4.4 【功能缺陷，P1】`resend_pool_ensure_relayhost` 无法为多个账号建立独立中继

**这是本次审查最重要的发现。** 该函数（`:168-186`）的设计目标是「号池每个账号对应一条 relayhosts 记录」，但实现如下：

```php
$label = 'Resend#' . $id;
$stmt = $pdo->prepare("SELECT `id` FROM `relayhosts` WHERE `hostname` = :h AND `username` = :u LIMIT 1");
$stmt->execute(array(':h' => RESEND_RELAY_HOST, ':u' => 'resend'));
//                              ^^^^^^^^^^^^^^^^ 常量 'smtp.resend.com:587'
//                                                          ^^^^^^^ 常量 'resend'（不随账号变）
if ($found) {
  // 已存在 → 用当前账号的 key 覆盖这条记录的密码
  $stmt = $pdo->prepare("UPDATE `relayhosts` SET `password` = :p, `active` = :a WHERE `id` = :id");
  ...
}
```

**问题**：`hostname` 与 `username` 都是**与账号无关的常量**。后果：

1. 账号 #1 首次调用 → 插入 `(smtp.resend.com:587, resend, KEY1)`。
2. 账号 #2 调用 → `SELECT` 命中 **#1 的那条**（因为 hostname/username 完全相同）→ 把 `password` **覆盖成 KEY2**。
3. 于是两个域名（`domain.relayhost` 都指向同一个 relayhosts.id）在发信时**共用 KEY2**。

**号池「多账号分散」的核心目的因此无法实现** —— 所有域名实际走同一个 Resend Key。同源问题也出现在 `resend_pool_assign:295`：

```php
$stmt = $pdo->prepare("UPDATE `domain` SET `relayhost` = :r WHERE `domain` = :d");
```

`$relay_id` 对所有账号最终是同一个 id，`domain.relayhost` 失去区分能力。

**当前状态**：线上 `resend_accounts=0`、`resend_domains=0`、`relayhosts` 中**无 `smtp.resend.com` 记录**，功能尚未投用 → **无法运行时验证**，本结论为**静态确认**。

**建议方向**（供决策，非本报告实施范围）：让 relayhosts 的标识随账号唯一，例如 `hostname` 用 `resend#<account_id>` 形式的占位再在 sasl 映射中改写，或直接以 `username` 区分（`username = 'resend'` → `username = 'resend#<id>'`），并保证 `domain.relayhost` 指向各自 id。**修复前请先用两条测试账号在 staging 实测两台 Resend Key 是否真正分离。**

## 七、不建议改动的部分

> 本节刻意区分「**真问题**」（见第二、五节）与「**教条式最佳实践**」。以下项目看似违反常规模范，但在 mailcow 场景下改动会**降低**价值或破坏兼容性。

### 7.1 不要改 `mailbox.attributes` JSON 存 relayhost 的设计

postfix 的三张热点映射表全部依赖 `JSON_VALUE(mailbox.attributes,'$.relayhost')`：

```sql
LEFT JOIN mailbox ON JSON_UNQUOTE(JSON_VALUE(mailbox.attributes,'$.relayhost')) = relayhosts.id
```

把这套 JSON 属性「规范化」成独立表，需要同步重写 20 个 `.cf` 映射 + PHP 全部读写路径，且**每次上游 mailcow 更新都会产生巨大冲突**。JSON 字段是上游**刻意设计**（灵活扩展属性、避免频繁 DDL）。虽然它导致该 JOIN 无法走索引，但在 `relayhosts` 只有个位数的现实下**代价为零**。

### 7.2 不要给 `domain.relayhost` 加索引来「优化」中继 JOIN

看似合理（消除 BNL join），实则：① 该 JOIN 由 `relayhosts`（4 行）全表扫描驱动，给 `domain` 加索引后优化器仍可能选全表扫描，收益不确定；② 更关键的是 **2.1 的自动清理机制** —— 手加的索引会被 `init_db_schema()` 删除，只能改 `init_db.inc.php`；③ `domain.relayhost` 是 VARCHAR 存 INT，加索引后跨类型比较仍无法完全利用索引。**CP 比不佳，不建议做。**

### 7.3 不要调大 `innodb_buffer_pool_size`

当前 24 MB 对 1.48 MB 的库是**过度满足**（命中率必然 100%）。调大只会挤占容器内存。上游 mailcow 默认值经受了大量生产验证，**保持不动**。

### 7.4 不要改 `utf8mb4_general_ci` 为 `_unicode_ci`

改排序规则需要重建全库 + 索引，且 mailcow 全链路（PHP/MySQL/SOGo/Dovecot）按 `general_ci` 测试。在邮件地址场景下两者差异极小，**收益不抵风险**。

### 7.5 不要为 `SELECT *` 做全量重构

`SELECT *` 是上游 mailcow 的普遍风格（46 处）。其成本在「宽表 + 全行已有缓存」的场景下可忽略，而重构会：① 产生海量无功能收益的 diff；② 每次上游更新都冲突；③ 引入漏字段的回归风险。**仅约束新代码写显式列名即可。**

### 7.6 不要给 `logs` / `sasl_log` 堆索引

这两张表是**高频写入**的日志表。mailcow 对其有自动清理机制，且日志查询多为「按时间倒序取前 N」。加过多的索引会拖慢写入、增大表体积，**收益存疑**。若日志页确实慢，优先考虑加 `created` 时间索引（单列），而非复合索引。

### 7.7 不要绕过 `init_db.inc.php` 直接做 DDL

由 2.1 揭示的同步机制决定：**任何不在声明中的索引都会被自动删除**。所有结构变更都必须经 `init_db.inc.php` + `$db_version` 递增。这是 mailcow 的核心可升级性保证，不可绕过。
