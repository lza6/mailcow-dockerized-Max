二、三个被实测推翻的直觉

直觉 1：「smtp_cf465 永不触发，是因为当前 relayhost 不是 :465」

实测推翻。 容器里 /opt/postfix.sh 的 md5 和仓库版本不同，且 一处 cf465 都没有。原因是 docker-compose.yml 里 postfix 用的是 ghcr.io/mailcow/postfix:3.10.12-1 预构建镜像、没有 build: 段 —— 仓库里的 postfix.sh 是打进镜像的，从未被使用。

所以 master.cf 里的连接器能加载（它是 bind mount），但选择它的逻辑根本没进来。这个「功能」在原部署里不存在。

直觉 2：「域名体检慢，是因为要查 13 个 RBL 名单」

部分推翻。 名单多只是表象。逐层测下来，真正的瓶颈是解析器链路：

测量结果
并发 5 个查询 → unbound 172.22.1.2541/5 应答，6.1 s
并发 5 个 → Docker 内嵌 127.0.0.11（冷）1–4/5，4.0 s
并发 5 个 → 内嵌（热）5/5，0.2 s
直连公共解析器的原始 RTT50–160 ms（稳定）

即：unbound 能串行服务、但不并发应答同一来源的多个在途 UDP 查询；而「网络慢」这个假设被彻底证伪。

直觉 3：「纯函数抽出来就能测了」

只对了一半。 抽出纯函数确实让判定逻辑可测了（60 条断言），但端点本身仍然测不到 —— 它 require 即执行。直到我真写了一层 prerequisites 桩去真跑端点，才暴露第二处缺陷：

Fatal error: Call to a member function hGet() on null
  in /tmp/e3/inc/ajax/domain_health.php:343

$redis->hGet('DKIM_SELECTORS', ...) 是该文件里唯一没有 if ($redis) 保护的调用（其余 6 处都有）。更隐蔽的是：$redis 为 null 时抛的是 Error（PHP 8 里不继承 Exception），而原代码只 catch (Exception) —— 拦不住。redis 一抖动，这个诊断页直接 500。而它恰恰是出问题时最该能打开的页。

四、踩过的坑（这部分最值钱）

1. Windows 检出直接构建镜像 → 容器 exit 127

core.autocrlf=true 且仓库没有 .gitattributes，工作区里 data/Dockerfiles/** 全是 CRLF。#!/bin/bash\r 让 exec 返回 ENOENT，supervisor 反复重启后 FATAL。

关键区分：git 索引里存的是 LF（实测 git show HEAD:...postfix.sh 的 CRLF 计数为 0），所以 Linux / 生产构建不受影响；只有在 Windows 上构建才会踩。

2. socket_select 返回后只 recvfrom 一次，会间歇性丢结果

select 只说「这个 fd 可读」，它的接收缓冲里可能排着多个应答。只读一次的话，剩下的包会一直躺着，而下一轮 select 未必再报这个 fd —— 表现是同一批查询「一次全中、一次全空」。

必须排空每个就绪 fd 的接收缓冲。

3. 拿「剩余总时长」当 select 的超时，会让排队的查询永远发不出去

一旦某轮 select 阻塞很久，后续查询就卡在 pending 里，最后整批一起超时。等待窗口要封顶（200 ms），让发送节奏不受阻塞时长影响。

4. 我一开始把「慢」归因给了错误的解析器

先改直连 unbound → 更糟（unbound 不并发应答）；再改回内嵌 → 仍不理想。最后用对照实验（同一批查询分别发到 unbound / 内嵌 / 公共解析器）才定位到真正可用的路径。不靠对照实验、只靠推理，会在这里反复来回。

5. 我的测试脚本自己写错了 3 处，一度被当成产品缺陷

TXT 的长度前缀我写错（chr(9) 应为 chr(2)）、MX 压缩指针指向的名字算错、把 dhc_dns_parse 的返回值当成 [] 而不是四键结构。测试写错会造成和代码错一模一样的现象 ——「失败了」不等于「产品坏了」。

变更测验

共 12 题，全部答对才算通过。选错会有解释。

1. 容器里 postconf -M | grep cf465 能看到 smtp_cf465 连接器，为什么说这个「功能」其实不存在？
「配置在」不等于「功能在」。要查一个改动是否真的生效，必须一路追到运行时真正读了哪个文件。
2. 要在默认部署里让仓库的 data/Dockerfiles/** 生效，正确做法是？
不启用 build: 的话，镜像永远来自 registry，本地源码改一百遍也不会进容器。
3. 为什么在 Windows 检出上重建镜像会导致容器 exit 127，而 Linux 上没事？
Dockerfile 里确实 chmod +x 了，所以不是权限问题 —— 是 shebang 行末尾多了 ，解释器路径变成 /bin/bash 。
4. 修复前那版 transport 判定，为什么说它「比什么都不做还差」？
TLS 方式必须跟随实际选中的下一跳，所以判定要用同一个 COALESCE。
5. catch (Exception $e) 为什么拦不住 $redis = null 时的 $redis->hGet()？
所以那处缺陷一直没被发现 —— 直到真跑端点才 Fatal。要抓「任何」错误得用 catch (Throwable)。
6. 域名体检原来 33.8 秒，主要时间花在哪？
定位手法是逐层计时 + 对照实验（同一批查询分别发到三种解析器），而不是猜。
7. 实测「并发 5 个查询到 unbound 只回来 1 个」，说明什么？
同一批查询串行发给它时 5/5 全中、耗时 0.16 s —— 证明不是坏了，是并发模型不匹配。
8. socket_select 返回某个 fd 可读后，为什么必须循环排空它？
症状极具迷惑性：同一批查询「一次全中、一次全空」，看起来像网络抖动。
9. 为什么「并发等待窗口」要用固定小值（如 200 ms），而不是用「剩余总时长」？
发送节奏不能被「等应答」的阻塞时长绑架 —— 这是把「发送」与「等待」解耦。
10. 新增的 test-dns-parse.php 用手工合成的报文而不是真实网络请求，主要理由是什么？
「CI 没网络」是顺带的好处，核心理由是可确定复现：NXDOMAIN、SERVFAIL、截断、自指压缩指针这些真实网络里偶发的情况，合成报文可以稳定测。
11. 我在这轮里「测试脚本自己写错 3 处」这件事，最该记住的教训是？
所以我在验证 DNS 原语时特意加了「Spamhaus 已知测试码必须能解析」这类已知答案断言。
12. 这轮把「纯函数抽出来」和「真跑端点」分成两步做，为什么？
只做前者会得到一个「测试全绿但页面 500」的假象。
