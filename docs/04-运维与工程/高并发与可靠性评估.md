# 高并发与可靠性现状评估

> 本文**只写已实测的事实**与**明确的结论**。
> 单机 mailcow 与"互联网级 SaaS"是两种东西 —— 有些基础设施在这里是**过度设计**，
> 硬上一套只会增加故障面。所以本文分三部分：已经有的 / 实测到的天花板 / 明确不建议做的。

---

## 一、已经具备的（有证据）

| 能力 | 现状 | 证据 |
|---|---|---|
| **健康检查** | mailcow 自带 `watchdog-mailcow` 每分钟巡检各服务并给出健康度；多个容器有 healthcheck | 实测输出：`PHP-FPM health level: 100%`、`Nginx 100%`、`MySQL 100%` 等 |
| **限流（入站/出站邮件）** | rspamd ratelimit + netfilter（fail2ban 式封禁，写 redis `BAN_LIST`） | `watchdog` 报 `Ratelimit health level: 100%`、`Fail2ban 100%` |
| **缓存** | redis：DKIM selector/公钥、域检查结果、审计计数、号池设置等，均带 TTL | `OV_RDAP` 24h、`OV_CHECK` 1h、`OV_AUDIT_COUNT` 60s |
| **应用层限流** | 体检动作有 20 秒 redis 互斥锁，折叠重复触发 | 实测第 2 次调用返回「体检刚刚执行过，请 18 秒后再试」 |
| **并发写安全** | 按目标 `GET_LOCK` 串行 + 死锁退避重试 | 600 次并发写同一邮箱：**0 失败 0 死锁** |
| **慢查询治理** | 自建表均按实际查询建了索引 | `overview_mbox_daily.day`、`warmup_log(plan_id,run_date)`、`warmup_messages.message_id` 等 |
| **数据保留** | ofelia 每日清理三张增长表（audit 180d / warmup_log 365d / daily 90d），分批删除避免长事务 | `data/conf/phpfpm/crons/retention.php` |
| **可观测（日志）** | 各容器日志 + 应用侧 `error_log`（异常只记日志、不回显内部细节）+ 管理操作审计表 | `admin_audit_log` 每次写动作留痕 |
| **备份/恢复** | 上游 `helper-scripts/backup_and_restore.sh` 可用 | 未改动 |

## 二、实测到的容量与天花板

| 场景 | 并发 | 结果 |
|---|---|---|
| 只读 AJAX（`action=overview`） | 1 / 10 / 25 / 50 | 1150 次 **0 失败**；峰值 ~123 RPS；P95 32ms → 566ms |
| HTML 页面（`/admin/overview`） | 10 / 25 / 50 | 600 次 **0 失败**；~80 RPS；P95 ≤ 911ms |
| 并发写同一邮箱 | 8 / 16 / 16 | 600 次 **0 失败 0 死锁** |
| 混合读写 | 4 读 + 4 写 | 160 次 **0 失败** |

**当前天花板：`php-fpm` 的 `pm.max_children = 50`**（web-worker 池）。
压测时 worker 数从 21 涨到 56，日志出现 `server reached pm.max_children setting (50)`。

- 表现是**延迟劣化而非失败**（第 51 个请求在 listen backlog 排队），这与"0 失败 + P95 明显抬升"的观测一致。
- **邮件收发不受影响**：postfix / dovecot / rspamd 是独立容器，全程 `restart=0`。

### 如果并发还要往上
1. **最直接**：调大 `data/conf/phpfpm/php-fpm.d/pools.conf` 里的 `pm.max_children`
   （受容器内存约束，一对一算：每个 worker 实测常驻几十 MB）
2. 给 `overview_build()` 的结果加 5–10 秒 redis 缓存（写操作后主动 DEL），
   把并发读折叠成一次重算 —— **这是投入产出比最高的一步**，目前每次刷新都是全量重算
3. 把首屏里那批查询拆成并行（现在是一条条串行）

## 三、**明确不建议**在这里做的（以及为什么）

以下都是"高并发标配"，但**对单机邮件服务器是过度设计**。写进来是为了避免以后有人
觉得"缺了就不专业"而硬上一套，反而增加故障面。

| 项 | 为什么不做 |
|---|---|
| **Load Balancer（流量分发）** | 单机部署没有第二个后端可分。真要多机，mailcow 的路径是 **replica 模式**（它自己支持 dovecot replication + redis slaveof），不是在前面加 nginx 层 |
| **CDN（静态加速）** | 后台页面只给管理员用，并发个位数；而且**响应是会话相关的**（cookie、CSRF），CDN 缓存不了也不该缓存 |
| **Database Replication（高可用）** | 本项目所有自建表都是**管理侧的辅助数据**（审计、养号、统计）。DB 挂了邮件照样收发（postfix/dovecot 有自己的队列与存储）。为这些数据上主从复制的收益远小于运维成本 |
| **Sharding（水平扩展）** | 规模是 16 个域 / 17 个邮箱。"分库分表"在这里是纯粹的自找麻烦 |
| **Message Queue（Kafka / RabbitMQ）** | 唯一接近队列需求的是养号发送，而**它恰恰需要慢**（Gmail 明确要求"别爆发"）。引入 MQ 去并发化会直接违背养号的设计目的。现有 ofelia 定时 + 单次批量上限（3 封）+ 全局日上限（30 封）就是正确的形态 |
| **Circuit Breaker（故障隔离）** | 现有外部依赖只有 Resend / Cloudflare / 收件人 IMAP。每个调用点已有**短超时 + 失败只影响单个对象**（一个收件人 IMAP 失败不会中断整轮），这已经是最朴素的熔断。为三个外部依赖引入熔断库不划算 |
| **Prometheus / 分布式追踪** | 单机 + 17 个邮箱，`docker stats` + 容器日志 + 审计表已够用。上 tracing 要先解决"谁来存、谁来查"的问题，收益不匹配 |

## 四、真正值得补的两件事（按性价比）

1. **`overview_build()` 结果缓存 5–10 秒**（写操作后 DEL）
   - 收益：并发读从"每次全量重算"变成"共享一次结果"，直接缓解 worker 池压力
   - 风险：最多 10 秒的数据延迟，对管理后台完全可接受
   - 注意：不能用固定 TTL 了事 —— 要配合**写操作主动失效**，否则管理员改完看不到变化

2. **让 `pm.max_children` 与容器内存形成明确关系**
   - 现在 50 是上游默认值，与本机内存无关
   - 建议先测出单 worker 的常驻内存，再按 `(容器内存 - 预留) / 单worker` 反算，写进注释

## 五、监测建议（不引入新组件）

| 想看什么 | 现有手段 |
|---|---|
| 谁在什么时候改了什么 | 后台「操作日志」= `admin_audit_log` |
| 服务是否健康 | `watchdog-mailcow` 日志（每分钟） |
| 页面快不快 | 页面右下角的加载耗时（AJAX 响应自带） |
| 有没有慢查询 | `docker exec mysql-mailcow mysql -e "SHOW FULL PROCESSLIST"` |
| 邮件是否真的发出去了 | 后台「投递链路追踪」按 Message-ID 串起 postfix → 中继 → 结果 |
| 养号效果 | 后台「养号」卡片的进箱率 / 垃圾箱率（来自收件人邮箱的真实核对） |
