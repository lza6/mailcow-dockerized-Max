一、上下文：我们当时面对什么

这不是一次「加个功能」的迭代。它起源于三个**看起来无关、其实同源**的现象。

现象 1：后台页面「有 16 个域名，但列表全空」

页面顶部的统计卡正常显示「域名 16 / 邮箱 16」，但下面所有表格一行都不显示。 养号标签页同样空白。浏览器控制台没有任何报错， 服务端返回的 HTML 里元素 ID 也一应俱全。

现象 2：点「进 Webmail」进的是管理员自己的邮箱

从某个邮箱行点进去，打开的是 SOGo，但登录身份是当前登录的管理员， 不是那个邮箱。

现象 3：养号是个黑匣子

只能看到「今天发了几封」。发给了谁、落到收件箱还是垃圾箱、下一封什么时候发、 对方有没有回复——全都看不到。而 Gmail 官方文档写得很清楚：按域记信誉、 量要慢慢涨、别爆发、要收件人主动互动。

关键判断：这三个现象里，只有一个是"配置问题"

现象 2 是我用错了链接（这是真 bug，但一眼可查）； 现象 1 和 3 表面无关，实际指向同一件事：整个系统缺少"可观测"这一层。 没有可观测性，连"页面到底渲染了什么"都只能靠猜——而我就是这么猜错的。

二、直觉：为什么第一反应是错的

面对现象 1，我的第一反应是「数据没传到前端」。于是我去查服务端返回的 HTML： 元素在；再查内联 JSON：16 个域名都在。于是判定「服务端没问题」。

这个判断错在哪里？错在把「服务端返回了什么」当成了「浏览器看到了什么」。 中间还有一整层我没看：前端 JS 在页面加载后到底对 DOM 做了什么。

真正的定位方式：在被怀疑的地方装上探针

与其继续读代码猜，不如把生产真实的页面 HTML + 真实 JS bundle 放进 jsdom 执行，然后钩住 DOM 写操作打印调用栈：

beforeParse(window) {
  const rc = window.Node.prototype.removeChild;
  window.Node.prototype.removeChild = function (child) {
    if (child.tagName === 'TBODY') console.log(new Error().stack);
    return rc.apply(this, arguments);
  };
}

调用栈直接落到了 bundle 第 2704 行——mailcow 自己的 footer.js：

$('tbody').filter(function(){ return $(this).children().length < 1; }).remove();

它在页面解析阶段就把所有空的 <tbody> 删掉了。 而我们的设计恰好是「tbody 留空、由 JS 填充」——容器先被删，JS 再写就找不到地方。 统计卡是 <div>，不受这条规则影响，于是出现了那个迷惑性的组合。

直觉修正：验证一个前端功能，必须验证「渲染后的结果」， 而不是「响应体里有没有东西」。这两者之间隔着一整个 JS 运行时。

三、做了什么

3.1 修掉真 bug：列表全空

动作说明
模板加占位行每个 <tbody> 放一行「正在加载…」，非空 → 不会被那条规则删；JS 渲染时整体替换

3.2 修掉真 bug：Webmail 进错账号

SOGo 的登录态由 mailcow 会话驱动（nginx auth_request → /sogo-auth-verify → sogo-auth.php， 通过 x-webobjects-remote-user 传当前登录用户）。 所以点 /SOGo/ 进去的永远是当前登录的那个人。

mailcow 官方的做法是 /sogo-auth.php?login=<邮箱>（见官方 mailbox.js），它会把会话切换到目标邮箱（dual-login）。 该入口需要 mailcow.conf 里 ALLOW_ADMIN_EMAIL_LOGIN=y—— 生产上原本是 n，已开启并实测通过。

变更测验

全部答对才算通过。选错会有解释。

1. 后台页面的表格全部空白，但响应体 HTML 里元素 ID 齐全、内联 JSON 有 16 个域名。最可能的原因是什么？
mailcow 的 footer.js 里有 $('tbody').filter(空).remove()，在解析阶段就执行。 容器被删后 JS 再 .html() 就写不进去；统计卡是 div 所以还在——这正是「有 16 个域名但列表全空」的由来。
2. 给写动作加「显式 CSRF 校验」时，为什么不能直接比对 $_POST['csrf_token'] 和会话里的 token？
改用「$_POST 是否被清空」作判据：框架只在失败时清空它。这个错我实际犯过，症状是"所有写操作 403"。
3. 「点进某个邮箱的 Webmail，进去的却是管理员自己」——正确修法是什么？
SOGo 的登录态由 mailcow 会话驱动，/SOGo/ 永远以「当前登录者」身份进入。 官方 mailbox.js 用的就是 sogo-auth.php?login=。
4. 判断养号邮件进了收件箱还是垃圾箱，为什么不能硬编码 [Gmail]/Spam？
IMAP 的 \Spam 属性是语言无关的，靠它定位才能在任意语言的账号上都正确。
5. 计算「垃圾箱率」时，为什么分母只算已判定的邮件（不含 unknown / missing）？
这是统计口径问题：一个健康度指标如果把"未知"当作"正常"，就会系统性高估健康度。
6. 为什么「显示邮箱登录密码明文」做不到？
这与"懒"无关，是密码学性质。可选的只有：重置后显示一次，或另建可逆加密的凭据记录（本次为养号收件人凭据做了后者）。
7. 「下一封什么时候发」为什么要和调度器共用同一个函数算？
这是「单一事实来源」原则在时间计算上的应用：同一个概念只能有一处定义。
8. 往远端推送时，为什么必须 cherry-pick 而不是直接 push 本地 master？
远端根提交是 Initial commit，本地根是上游 mailcow 的完整历史。git merge-base 退出码 1、无输出。
9. 判断"这个按钮是不是假的"，最有说服力的做法是什么？
本次用脚本审了 47 个控件，抓出 1 个没有处理器的 ov_pool_reveal。手工看容易漏。
10. 这次修复中，最该记住的方法论是哪一条？
这次的根因隐藏了足够久，正因为最开始把"响应体里有元素 ID"当成了"页面正常"。
