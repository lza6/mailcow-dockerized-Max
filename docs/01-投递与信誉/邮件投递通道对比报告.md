# 邮件投递通道对比与实测报告

> 测试日期：2026-10-08 ~ 10-09
> 涉及：15 个发件域、3 条投递通道、400+ 封实测邮件
> **本报告所有数字均为实测，不含推测。无任何密钥。**

---

## 一、核心结论（先看这个）

**技术配置不是决定因素，域名自身的历史信誉才是。**

实证：同一套配置、同一个 Resend 账号、认证全部 `dkim=pass spf=pass dmarc=pass`，
两个域的表现**连续 3 轮 100% 稳定分化**：

| 根域 | 第 1 轮 | 第 2 轮 | 第 3 轮 | 进箱率 |
|---|---|---|---|---|
| `indigobasketglobal.com` | ✅ 收件箱 | ✅ 收件箱 | ✅ 收件箱 | **100%** |
| `urbansproutglobal.com` | ❌ 垃圾箱 | ❌ 垃圾箱 | ❌ 垃圾箱 | **0%** |

配置完全相同，结果完全相反。**唯一变量是域名。**

## 三、通道一：直发（自建服务器）—— 已淘汰

**配置**：OVH VPS（`15.204.205.80`，AS16276）+ 自建 mailcow

| 测试 | 结果 |
|---|---|
| SPF / DKIM / DMARC | **全部 pass**（Gmail + Port25 双重验证） |
| 16 个域直发 Gmail | **100% 进垃圾箱** |
| 连注册 152 天的 pony-it.com | **同样进垃圾箱** |
| 4 种内容变体（纯文本/中文/HTML/带退订头） | **全部进垃圾箱** |

**根因**：OVH 数据中心 IP（`hosting: true`）、零发信信誉、域名全新、无收件人关系。

**已排除的因素**：认证配置、邮件内容、域名年龄（单看）、DNS 设置。

**进箱率：0%**

## 四、通道二：Cloudflare Email Sending

### 4.1 硬限制：只支持子域

实测确认：

```
daniel@send.urbansproutglobal.com   → ✅ 发送成功
daniel@urbansproutglobal.com        → ❌ HTTP 400 email.sending.error.email.invalid
```

**Cloudflare 的 DKIM 签名域是 `send.<域名>`**（`s=cf-bounce, d=send.<域名>`），
用根域发信会导致签名域与 From 域不一致，因此 CF 直接拒绝。

### 4.2 实测数据（子域）

| 发件人 | 收件箱 | 垃圾箱 | 进箱率 |
|---|---|---|---|
| `send.breezeshelf.com` | **16** | 0 | **100%** |
| `send.urbansproutglobal.com` | 5 | 3 | 63% |
| `send2.urbansproutglobal.com` | 3 | 0 | **100%** |
| 其余子域（批量测试） | 0 | 2-3 | 0% |

### 4.3 实测数据（根域）

| 根域 | 收件箱 | 垃圾箱 |
|---|---|---|
| 15 个域的根域 | **全部 0** | 3-4 |

**根域进箱率：0/31 = 0%**

### 4.4 速率限制（实测）

```
第 1 轮 15 封（间隔 25 秒）   → 全部受理
第 2-4 轮 45 封              → 全部 HTTP 429 (email.sending.error.throttled)
```

官方说明：**新账号从保守的日配额起步，随发信行为与信誉自动放宽**，不公开具体数值。

### 4.5 技术集成障碍（已解决）

CF 只接受 **465 + 隐式 TLS**，而 mailcow 无法指定 465：

| 机制 | 限制 |
|---|---|
| `sender_dependent_default_transport_maps` | 只接受纯主机名（传 `transport:host` 会让 postfix 崩溃） |
| `transport_maps` | 按**收件人**匹配，无法按发件域路由 |
| mailcow 生成的 SQL | 硬编码 `smtp:` 前缀，且容器**每次启动重新生成** |

**解法**：`helper-scripts/cf-email-bridge/`（SMTP 桥接，无需重建镜像）
```
mailcow postfix ──明文──> cf-bridge:2526 ──隐式TLS 465──> Cloudflare ──> 收件方
```
实测通过：`relay=cf-bridge[172.22.1.14]:2526`，桥接成功连 CF 465 并认证。

## 五、通道三：Resend —— 支持根域

### 5.1 核心优势

**Resend 允许用根域发信**：`sophia@hearthcart.com`、`noah@indigobasketglobal.com` 均发送成功。

### 5.2 实测数据（根域）

| 根域 | 收件箱 | 垃圾箱 | 进箱率 |
|---|---|---|---|
| `indigobasketglobal.com` | **3** | 0 | **100%** |
| `urbansproutglobal.com` | 0 | **3** | **0%** |
| `hearthcart.com` | 域名未验证完成，无法发信 | — | — |

**认证全部 `dkim=pass spf=pass dmarc=pass`。**

### 5.3 免费版硬限制（实测）

```
POST /domains → HTTP 403
{"message":"You have reached the domain limit of your plan. Upgrade to add more."}
```

**Resend 免费版只允许 3 个域名。**

已成功接入 3 个：
- `indigobasketglobal.com` — verified
- `hearthcart.com` — verified
- `urbansproutglobal.com` — verified

**其余 12 个域无法接入**，除非升级付费计划。

### 5.4 一个必须注意的坑（实测踩到）

Resend 后台显示域名"已验证"，但**实际 DNS 记录可能已不存在**。
用 API 重建域名前，实测发现 `hearthcart.com` 的 4 条 DNS 记录（DKIM/SPF/MX/CNAME）
在 Cloudflare 里**一条都没有**，导致邮件带着 `dkim=permerror dmarc=fail` 发出。

**处理**：通过 API 删除域名并重建，重新写入 DNS 记录后才正常。

## 七、选型建议

### 场景 A：必须用根域

| 选项 | 条件 |
|---|---|
| **Resend** | 需接受**免费版 3 个域限制**；升级付费可加域 |
| 自建直发 | 需先解决 IP 信誉（数月积累）+ 换到开放 25 端口的服务商 |

### 场景 B：可用子域

| 选项 | 进箱率 |
|---|---|
| **Cloudflare Email Sending** | 子域实测 **100%**（`send.breezeshelf.com` 16/16） |
| Resend 子域 | 未单独测，但 Resend 同样支持子域 |

### 关键提醒

**无论走哪条通道，域名的历史信誉都是决定性因素。**
`indigobasketglobal.com` 与 `urbansproutglobal.com` 在完全相同的配置下，
进箱率分别是 100% 与 0%，且连续 3 轮稳定复现。

**提升进箱率的实际手段**（按有效性排序）：

1. **让收件人点「不是垃圾邮件」** —— Google 对此权重极高
2. **集中使用 1-2 个已有正向记录的域** —— 而非同时启用 15 个新域
3. **控制发送节奏** —— 新域前 30 天建议每天不超过 20-50 封
4. **给域名建站** —— 多数域连 A 记录都没有，接收方会参考
5. **加 `List-Unsubscribe` 头** —— 收件箱内正常邮件 100% 都有
