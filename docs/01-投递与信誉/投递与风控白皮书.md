## 阅读前的一句话

**邮件能不能进对方的收件箱，本质上是一个概率问题，不是一个能"配好就永久解决"的开关。**
我们能做的，是把概率尽量往"进收件箱"的方向推；任何人都无法承诺"100% 进收件箱"。
凡是声称能做到 100% 的说法，要么在骗人，要么用的是会被惩罚的作弊手段（例如刷假的"打开率"）。

## 一、为什么邮件会进垃圾箱

### 1.1 先建立最关键的一个概念：发件信誉

想象你收到一封推销信：

- 如果它来自一家**你听说过的老字号**，你会打开看看；
- 如果它来自一个**昨天刚注册、连店面都没有的新公司**，你大概率直接扔掉。

Gmail、Outlook 这些收件方，就是在替收件人做这个"要不要扔掉"的判断。
它们心里对每个发件方都有一本账，这本账叫**发件信誉**。

> **发件信誉（Reputation）**：收件方根据你过去"发了多少、别人怎么反应（打开/回复/举报）"累积出来的一个信任分。
> 它不是你自己填的，是收件方**偷偷给你打的分**，你平时看不到，除非用官方工具才能查到（见第五节）。

信誉的脾气很怪，必须记住两句话：

1. **涨得慢** —— 从零开始攒一个"可信"的印象，通常要以**周**、甚至**月**为单位。
2. **掉得快** —— 一次突然的批量群发，可能让几周的积累一夜归零。

### 1.2 收件方是怎么判定的：四层

收件方在决定"收件箱还是垃圾箱"时，大致看四层。**四层全过关，才最可能进收件箱；任何一层弱，都会被往下压。**

| 层 | 大白话解释 | 出问题时长什么样 |
|---|---|---|
| **① 认证（技术层）** | 证明"这封信真的是我发的，没被人冒名"——相当于出示**身份证** | 邮件头上写着 `spf=fail` / `dkim=fail` |
| **② 信誉（历史层）** | 你过去的"生意口碑"好不好——相当于**老字号 vs 新开的店** | 认证全过，但照样进垃圾箱（本项目的核心事实） |
| **③ 内容（写了什么）** | 信的正文有没有像垃圾广告（全是感叹号、夸张承诺、"点击领奖"） | 命中垃圾词、被本机反垃圾打高分 |
| **④ 行为（怎么发的）** | 你发信的**节奏和方式**，是不是像机器人在批量轰炸 | 短时间给一大堆人/一大堆域同时发信（"突发发送"） |

> **项目实测的重点**：本项目历史上**第①层（认证）已经全过**，邮件还是进垃圾箱。
> 所以问题出在②③④，尤其是**第②层（信誉）**和**第④层（行为）**。这正是本文后面反复强调这两层的原因。

### 1.3 为什么"认证全过"仍会进垃圾箱（本项目实测的核心事实）

这是本项目投入最多时间才弄明白的一件事，也是整个白皮书最重要的一节。

**先看证据（这些都是真实抓取的原文，不是我们的推测）：**

Gmail 自己返回的认证判定（从收到的邮件头里提取的原文）：

```
Authentication-Results: mx.google.com;
    dkim=pass  header.i=@urbansproutglobal.com header.s=dkim;
    spf=pass   (google.com: domain of ... designates 15.204.205.80 as permitted sender);
    dmarc=pass (p=NONE sp=NONE disNONE) header.from=urbansproutglobal.com
```

第三方权威验证器 **Port25** 的独立复核报告（我们向它的 `check-auth@verifier.port25.com` 发信后，它自动回了一封报告）：

```
SPF check:     pass
"iprev" check: pass      ← 反向解析与 HELO 一致
DKIM check:    pass      ← d=urbansproutglobal.com, s=dkim, 2048-bit
```

**这两份材料的含义：**

- 第一份是**收件方（Gmail）自己说的**——不是我方自吹，是对方权威判定，三项全 pass；
- 第二份是**独立第三方**的复核——换一个机构再验一次，依然全 pass。

**结论：认证这一层满分；但邮件仍然进垃圾箱。** 这直接证明：
**"认证通过 ≠ 进收件箱"。** 认证只是入场券，不是进门证。

再补一条本项目实测的硬数据，说明拦截发生在"信誉模型"而不是别处：

- 把发件域名换成已注册 **152 天**的老域（pony-it.com），结果**完全一样，还是进垃圾箱**；
- 把邮件内容换成最简单的纯文本、中文、HTML、带退订头共 4 种变体，结果**完全一样**；
- 用权威解析器查了 **13 个主流黑名单**，发信 IP 基本都没被列入。

也就是说：**不是因为内容差、不是因为被拉黑、也不是单看域名年龄**。
拦截发生在 Gmail 内部的"信誉/年龄模型"里——它看到的是一个**刚刚冒出来、还不知底细的发件方**。

### 1.4 本项目最反直觉的一条实测发现（务必记住）

同一批域、同一套配置、同一个收件人，**"单独发一封"和"混在 15 封里一起发"，结果完全相反**：

| 场景 | 认证 | 落点 |
|---|---|---|
| 同一个域，**单独发 1 封** | pass / pass / pass | ✅ **进收件箱** |
| 同一封，**混在 15 封批量里发** | pass / pass / pass | ❌ **进垃圾箱** |

另一组更极端的对照：在 **2 小时之内**，同一批域从「6/6 进收件箱」翻转为「0/6 全进垃圾箱」——
**配置一个字没改，只是连着多发了几封。**

**这说明：决定落点的关键，往往不是"你的域好不好"，而是"你这批信是怎么发出去的"。**
"批量突发"是收件方最忌惮的行为特征之一。

## 二、我们做了什么（以及为什么这么做）

### 2.1 三张"通行证"：SPF / DKIM / DMARC

可以把发信想象成"去一家严格的门店办事"，需要三样东西：

| 名称 | 类比 | 它解决什么问题 | 一句话原理 |
|---|---|---|---|
| **SPF** | **身份证 / 门禁名单** | 防止别人冒用你的域名发信 | 在 DNS 里声明"只有这几台机器有权代表我发信" |
| **DKIM** | **防伪签名** | 证明这封信在途中没被篡改 | 用私钥给信签个名，对方用 DNS 里的公钥验签名 |
| **DMARC** | **门规 / 处置策略** | 告诉对方"发现冒名信时该怎么办" | 规定"认证不过的信，请你拒收/隔离/放行" |

> **DNS 是什么**：可以把域名想象成一个"电话簿"。你在里面一条一条登记信息（"我的邮件服务器是这台""我的公钥是这个"），全世界都能来查。
> SPF、DKIM 公钥、DMARC 全是登记在这个"电话簿"里的条目。

本项目这 16 个域的实测结果：**SPF、DKIM、DMARC 全部配置正确、全部验证通过**（16/16）。
**所以这一层不是我们的短板——但请记住，它不是万能的（见第一章）。**

### 2.2 为什么用"中继 + 号池"，而不是拿自己的服务器直接发

**先说自己的服务器直接发（业内叫"直发"）为什么吃亏。**

发件信誉是**逐个 IP 地址**累积的。你自己新买的一台服务器 IP，在收件方眼里就是一个"昨天才出生的陌生人"，
信誉是**零起点**。更雪上加霜的是：国内外主流云厂商**约 90% 默认封掉 25 端口**（发邮件必须走的端口），
很多机器压根发不出去。本项目实测：香港、美国两台备用机，25 端口**出站全被封**。

**所以我们的做法是"搭车"——通过专业中继服务商发信。**

```
直发（我们自己的服务器）：
  我们的服务器(全新冷 IP) ──25端口──> Gmail      ❌ 25 端口可能被封 / 信誉零起点

中继（搭专业服务商的车）：
  我们的服务器 ──587端口──> 中继商(高信誉 IP 池) ──25端口──> Gmail   ✅
                              ↑
                        587 端口所有云商都开放
```

> **中继（Relay）**：一个专门的"邮件转运公司"。你把信交给它，它用自己的高信誉 IP 帮你把信送到目的地。
> 相当于：你自己送货没人信，但交给顺丰,对方就认。
> **号池**：因为有服务商限制"一个账号只能绑 3 个域名"，而我们域名多，就把**多个服务商账号凑成一个池子**，轮流用，凑够容量（详见 2.4）。

**中继解决了什么：** ①绕开 25 端口封锁；②不必从零养一个 IP 的信誉——直接用服务商积累多年的信誉。
**代价（必须接受）：** 邮件内容和签名密钥会经过第三方，我们失去一部分"源头控制权"。这是搭车的固有成本。

### 2.3 为什么要"养号"（Warmup）

既然中继商的 IP 信誉好，为什么还要养？因为**中继改变不了"你是个新发件方"这件事**。
中继用的是共享 IP 池，同一个域今天可能落在信誉好的 IP 上（进收件箱），明天落在被别人用脏的 IP 上（进垃圾箱）。

**养的，是"你域名自己"的信誉。** 方法就是**模仿一个正常人的收发节奏**：

- 量要**慢慢涨**，不能今天发 10 封、明天发 1000 封（那叫"突发"，是垃圾邮件的典型特征）；
- **分散在一天里的不同时刻**发，别集中一个点爆发；
- 收件人要是**真实会打开、会回复**的人——收件人的正面互动，是收件方最看重的信号；
- 一旦被举报的比例超过红线（0.30%），**立刻停发**。

本项目已经把这套节奏做成了自动化功能（"养号功能"），系统会按计划、低速、分散地自动发送，
并在失败率过高时自动暂停。**注意：养号不是发一两封就能见效的**——判定改变通常要以**周**计，
判断标准是"随时间推移，进箱率有没有上升"，而不是"第一封是否进箱"。

> 一条重要的认知：**"暂停不发"是中性、无害的；"乱发/爆发"才是有害的。**
> 所以宁可让一个域先闲着，也不要为了"都用上"而今天发一点、明天发一点。

### 2.4 为什么每个域配独立的号池账号

因为我们有 15 个发件域，而多数中继服务商的免费版**一个账号只能绑 3 个域名**（Resend 免费版就是 3 个）。
15 个域至少要 5 个账号才装得下。

更重要的是**隔离风险**：

- 如果所有域共用一套配置，**一个域出问题（被举报、被降级），可能牵连到其它域**；
- 每个域（或每组域）走**独立的账号、独立的出口**，出了问题能**把损失锁在局部**，不波及全局；
- 本项目后台有专门的「**中继号池**」页面，可以把域名分配给不同账号，界面上一眼能看到"哪个域走哪个账号、每个账号还剩多少容量"。

## 三、实测的权威证据

> 本节的所有数字和原文都取自本项目 `docs/01-投递与信誉/` 下的实测报告，**未做改写**。
> 强调：这些**不是我们自己说的**，是 **Gmail 自己返回的判定** + **独立第三方验证器复核** + **权威注册数据（RDAP）** 交叉印证的。

### 3.1 证据一：认证全过，仍然全进垃圾箱（15 个根域逐域实测）

本题最核心的一组数据。**经生产真实链路**（postfix → cf-bridge → Cloudflare）逐域实发到 Gmail 测试号，
再用 IMAP 读取真实落点：

**结论：进箱 0/30（两轮各 15 封），垃圾箱 30/30。其中 14 个域的 DKIM/SPF/DMARC 全部 pass，照样进垃圾箱。**

| # | 发件域 | 落点 | DKIM | SPF | DMARC |
|---|--------|------|------|-----|-------|
| 1 | urbansproutglobal.com | ❌ 垃圾箱 | pass | pass | pass |
| 2 | breezeshelf.com | ❌ 垃圾箱 | pass | pass | pass |
| 3 | brightcrateglobal.com | ❌ 垃圾箱 | pass | pass | pass |
| 4 | **cedarcartco.com** | ❌ 垃圾箱 | pass | **FAIL** | **FAIL** |
| 5–15 | cedarloomexporthouse / echolanecommerce / harborpinetradeworks / hearthcart / indigobasketglobal / larkhavensupplyworks / mangobridgeretail / maplevalleytrading / summitnestretail / trendhollowretail / xiaomillc | ❌ 全部垃圾箱 | pass | pass | pass |

> 注：第 4 个域（cedarcartco.com）认证当时确有缺陷（已修复），其余 14 个认证**全部通过**却无一进箱。
> **这再次证明：认证通过 ≠ 进箱。**

### 3.2 证据二：真实原因不是"配置错误"，而是"域名的注册画像"

用 **RDAP**（域名的权威注册数据，相当于域名的"户口本"）查了这 15 个域的注册时间：

| 注册日期 | 域名数 |
|----------|-------:|
| **2026-09-22** | **13 个（同一天）** |
| 2026-09-23 | 1 |
| 2026-10-03 | 1 |
| 2026-10-06 | 2 |
| 2026-10-07 | 1 |
| pony-it.com | 2026-05-09（154 天，明显更老）|

**15 个域全部在 18 天内注册，其中 13 个集中在同一天。**

其它共同特征：**15 个域用同一对 NS 服务器**、网站全指向**同一个 IP**、多数站点连不上、**MTA-STS 记录 15/15 全缺**、DMARC 全是 `p=none`。

这些特征组合起来，正是 Google 反垃圾文档里描述的
**"批量注册、无真实业务、同源基础设施"** 模式——在收件方眼里，这不是 15 个独立域，而是**一个可疑的集群**。

### 3.3 证据三：落点取决于"这一次投递用的出口 IP"（不是你的域）

用同一个中继、同一个发件域、同一个收件人连发多封，**认证逐字节一致，落点却不同**：

| 时间 | 落点 | 出口 IP | DKIM | SPF | DMARC |
|------|------|---------|------|-----|-------|
| 17:28:36 | ✅ 收件箱 | 45.158.83.**4** | pass ×2 | pass | pass |
| 17:53:42 | ✅ 收件箱 | 45.158.83.**7** | pass ×2 | pass | pass |
| 17:57:16 | ❌ 垃圾箱 | 45.158.83.**28** | pass ×2 | pass | pass |
| 19:51:49 | ✅ 收件箱 | 45.158.83.**1** | pass ×2 | pass | pass |

**认证头完全一致，唯一变量是这次轮换到的共享出口 IP。**
这解释了一个长期困惑：为什么同一个域、同样配置，一会儿进箱一会儿进垃圾箱——
因为判定对象不只是"你的域"，**还包括"这一次投递所用的那个 IP 的个体信誉"**。

### 3.4 证据四：各通道实测进箱率对比（共 299 封实测）

| 通道 | 进箱 | 垃圾 | 进箱率 |
|------|-----:|-----:|-------:|
| 直发（OVH IP 15.204.205.80） | 36 | 201 | **15.2%** |
| Cloudflare 中继 + 根域 | 16 | 40 | **28.6%** |
| Mailtrap 中继（官方 demo 域） | 6 | 1 | **≈ 85.7%** |

**怎么读这张表：**

- 直发最差（15.2%），印证"自建冷 IP 不可行"；
- **Mailtrap 的 85.7% 用的是它官方长期运营的 demo 域**，信誉本来就好——
  **换成我们自己的 18 天新域，同样的通道未必能复制这个成绩**（这就是为什么"换个通道就万事大吉"是错觉）；
- 通道能帮忙，但**帮不了"域本身太新 + 短时间批量连发"这一层**。

### 3.5 证据五：IP 没有被拉黑

对实际发信 IP 查了 11 个主流黑名单（用权威解析器）：

| IP | 归属 | 结果 |
|----|------|------|
| `104.30.16.152` | Cloudflare 发信 IP | **11/11 全部未列入** |
| `15.204.205.80` | 自有服务器直发 IP | **10/11 未列入** |

> 一个小陷阱：用公共解析器（如 1.1.1.1）查 Spamhaus，有时会返回 `127.255.255.254`。
> 这**不是"被拉黑了"**，而是"该解析器不允许用 Spamhaus 的免费查询"。别被它吓到。

**结论：不是被拉黑，拦截发生在收件方内部的信誉模型里。**

## 四、排查手册（可照着做）

> **第一原则：先分清是"入站"还是"出站"。** 两者根因完全不同，混着查会白费大量时间。

| 方向 | 症状 | 第一件事查什么 |
|---|---|---|
| **出站** | 我们发出去的邮件、对方进垃圾箱 | 对方返回的 `Authentication-Results` 认证头 + 出口 IP 信誉 |
| **入站** | 我们**收不到**别人的邮件、收不到验证码 | **MX 记录**（决定外部邮件投到哪台服务器）|

---

### 4.1 出站排查（我们发出去进了对方垃圾箱）

**按顺序走，每一步都告诉你"看到 X 说明 Y"。**

#### 第 1 步：看对方返回的"认证头"

让对方（或你发测试邮件的那个 Gmail）把收到的邮件**原始头**给你，找到 `Authentication-Results` 这一行。

- **看到 `dkim=pass spf=pass dmarc=pass`** → 认证没问题，**别再去改 DNS 了**，问题在信誉/行为层（跳到第 5 步）。
- **看到 `spf=fail`** → 你的 SPF 没包含"实际发信的出口 IP"。如果你用了中继，**中继商的 IP/域名必须写进 SPF**，否则中继后 SPF 会 fail，**比直发还糟**。
- **看到 `dkim=permerror` 或 `no key for signature`** → DNS 里查不到 DKIM 公钥，或**签名用的 selector 和 DNS 记录名对不上**（这是最常见的 DKIM 失效原因：签名头里 `s=` 是什么，DNS 记录就得叫 `<那个值>._domainkey.<你的域>`）。
- **看到 `dmarc=FAIL`** → 通常是 SPF 或 DKIM 至少一个没过连带的。

在后台哪里看：**管理员后台 → 系统 → 域名健康**（对某个域点点看，会给出一项项判定与修复建议）。

#### 第 2 步：用第三方验证器交叉验证

光看一封邮件不够，可以主动要一份独立报告。向这两个地址各发一封**空白测试邮件**，它们会自动回一份详细报告到你的发件箱：

- `check-auth@verifier.port25.com` —— 回一份含 `SPF` / `iprev` / `DKIM` 明细的报告。
- （Gmail 自己的判定则以第 1 步的认证头为准。）

**看到三项全 pass** → 技术层确认没问题。
**看到某一项 fail** → 回到第 1 步对应的项去修。

报告会回到你自己的邮箱。取用命令（在服务器上，把 `<user>` 和 `<UID>` 换成实际值）：

```bash
docker exec $(docker ps -qf name=dovecot-mailcow) doveadm fetch -u <user> text mailbox INBOX uid <UID>
```

#### 第 3 步：查 DNS 四条记录

在**权威解析器**上查（避免本地缓存给你的旧结果）：

```bash
dig +short TXT <你的域> @1.1.1.1                          # SPF
dig +short TXT _dmarc.<你的域> @1.1.1.1                   # DMARC
dig +short TXT <selector>._domainkey.<你的域> @1.1.1.1    # DKIM 公钥
dig +short -x <服务器IP> @1.1.1.1                         # PTR（反向解析）
```

- **SPF 看到 `v=spf1 ... -all`** → 正常（`-all` 表示"未授权的一律拒绝"，是推荐写法）。**看到以 `~all` 结尾** → 较宽松，也能用。**什么都没返回** → 没配 SPF，必须补。
- **DMARC 看到 `v=DMARC1; p=none;`** → 只监控不拦截，对投递提升有限；条件成熟再收紧到 `p=quarantine`。
- **DKIM 看到一大串公钥** → 正常。**什么都没返回** → 公钥没发布，签名必然验不过。
- **PTR 必须和你的邮件主机名一致**（本项目是 `mail.pony-it.com`）。**不一致** → 多数接收方会扣分，去主机商那边改反向解析。

#### 第 4 步：查黑名单（别被误报吓到）

```bash
dig +short <把IP反过来>.zen.spamhaus.org @<一个权威解析器>
```

- **有结果（返回 127.0.0.x）** → 可能真被列入，去该名单官网申请移除。
- **返回 `127.255.255.254`** → **这不是拉黑**，是"公共解析器被拒绝查询"。换一个自建/权威解析器再查。
- **本项目实测两个 IP 都干净**——所以别把"进垃圾箱"简单归因为"被拉黑"。

#### 第 5 步：认证都没问题，但仍然进垃圾箱 → 看"内容"和"行为"

到这里说明是第②③④层的问题。按顺序自查：

- **内容层**：正文是否像广告（全大写、一堆感叹号、"限时""点击领取"）？正常批量邮件应带 `List-Unsubscribe`（退订）头——本项目实测收件箱里的 60 封正常邮件**100% 都有**这个头。
- **行为层（最关键）**：
  - **是不是短时间给很多人/很多域一起发了？** 这是本项目唯一被反复验证的触发因素。**把它从"一次几十封"改成"一天几封、分散在不同时刻"。**
  - 是不是反复给**同一个收件人**发测试邮件？这会把收件端的信号喂坏（Gmail 会看收件人对这封信做了什么：打开/回复/标非垃圾/删/举报）。
  - 是不是**同时启用了太多个新域**？两个实测都说明：15 个新域同时在发，在收件方眼里是**一个集群**，会互相牵连。
- **信誉层**：如果域名很新、又没网站内容，收件方会天然保守。可以给主域做**真实网站内容**（本项目有些域连 A 记录都没有，收件方会参考）；接入 **Google Postmaster Tools** 看官方信誉分（见第五节）。

---

### 4.2 入站排查（我们收不到别人的邮件）

**第一件事，且基本是唯一一件事：查 MX 记录。**

MX 记录决定"外部发给你的邮件，投到哪台服务器"。**如果 MX 指到了别人家，邮件永远不会到你的机器上，你这个邮箱自然什么都收不到。**

```bash
dig +short MX <你的域> @1.1.1.1
```

- **看到 `10 mail.pony-it.com.`** → 正常（要和你所有域的 MX 保持一致）。
- **看到别的服务器（例如某个第三方主机）** → **这就是根因。** 去 DNS 服务商（本项目用 Cloudflare）把 MX 改回 `mail.pony-it.com`（优先级 10）。

**本项目真实案例**：`breezeshelf.com` 的 MX 曾被指向第三方免费主机 `mail16.serv00.com`，
结果该邮箱**完全收不到外部邮件，连登录验证码都取不到**；其余 15 个域 MX 都正确，只有这一个漂移了。
改回 `mail.pony-it.com` 后即恢复正常。

**改 MX 后怎么确认修好了（三步互证）：**

1. 用权威解析器再查一次 MX，确认已改为 `mail.pony-it.com`；
2. 从**外部**（例如一个 Gmail 账号）实发一封到该邮箱；
3. 在服务器看日志，找到类似这一行：
   ```
   to=<某邮箱>, relay=dovecot, status=sent (250 ... Saved)
   ```
   **看到 `status=sent ... Saved`** → 邮件已成功落入邮箱，入站链路通了。

> 排查入站故障的三件互证工具：①`mailbox` 表确认邮箱存在且启用；②postfix 日志确认该域**只有出站、没有入站投递**（没有入站记录是断链的决定性信号）；③doveadm 看邮箱邮件数有没有增长。

> **提醒**：MX 指错期间，那段时间发给该域的邮件已经投到了错误的主机，**找不回来了**——需要对方**重新触发一次**（例如重新发验证码）。

## 五、日常维护

### 5.1 养号什么时候可以停？

不要凭感觉停。满足下面**全部**条件再停，才是稳妥的：

| 判断项 | 达到什么标准才算"可以停" |
|---|---|
| **进箱率稳定** | 在**中等发送量**下，抽样进箱率**持续稳定在高位**（不要再出现"忽好忽坏"的大波动），且这个状态保持了一段观察期（例如连续 2–4 周）。 |
| **天数走完** | 养号计划里设定的**总天数已经走完**（计划表里会显示"第 N/M 天"）。 |
| **域龄足够** | 域名注册时间达到 **3–6 个月**（域名年龄是收件方的硬指标之一）。 |
| **官方信誉分达标** | 在 **Google Postmaster Tools** 里，域名信誉稳定在 **High / Medium**（不是 Low/未知）。 |
| **举报率达标** | 垃圾邮件举报率持续 **< 0.10%**（红线 0.30%），硬退信率 **< 2%**。 |

**只要有一项不达标，就继续养、或者减量观察。** "暂停不发"没有惩罚，但"提前放量"会前功尽弃。

> 一句话：**信誉是概率，不是开关。** 养号能显著提高进箱概率并让结果可持续，但永远做不到"保证 100% 进收件箱"。

### 5.2 怎么加新域名

1. **在 DNS 里配好这个域的基础记录**：MX（指向 `mail.pony-it.com`）、SPF、DKIM 公钥、DMARC。
   —— 最省事的办法是用后台的「**域名总览 → 添加域名**」，或用「域名健康」逐项检查，缺哪项补哪项。
2. **在 mailcow 里添加域名**（如果是转发中继，配置它作为域）。
3. **为该域在中继服务商那里验证域名**（拿到对方要求的 SPF/DKIM 记录，写进 DNS）。本项目有「**中继号池**」页面：
   - 填域名 + 选一个**还有剩余容量**的账号 → 点「绑定」；
   - 系统会自动在服务商侧建域、写 DNS（若配了 Cloudflare Token）、触发验证、并把这个域的出站切到对应账号。
4. **在后台确认验证状态**（域名列表里会显示 `verified` 等徽章），必要时点「同步验证状态」刷新。
5. **让新域从"养号第 1 天"开始**，不要一上来就接大流量。

> ⚠️ **新域切记**：**不要把 URL/图片/正文指向从未建站的空壳域，也不要一注册就大批量发信**——这正是本项目踩过的坑（15 个同天注册的域被判定为一个可疑集群）。

### 5.3 怎么加新的号池账号与 API Key

> **先明确红线**：API Key 属于机密，**不要把它写进任何文档、聊天记录或截图**。添加后在界面上只显示掩码（形如 `re_xxxxxx…xxxx`）。

1. 去中继服务商后台，**创建一把 API Key**，权限必须选 **Full access**（本项目实测：只有"仅发信"权限的 Key 会被拒绝，因为读不了域名列表）。
2. 打开 mailcow 后台「**中继号池**」页面 → 「添加账号」区。
3. **粘贴 Key**（可填一个便于识别的标签，如"账号 A/主号"），先点「**测试 Key**」确认有效，再点「**＋ 添加**」。
4. 账号入池后，可用「**自动分配全部域名**」把域名分配到容量最大的账号；也可以手动逐个绑定。
5. 绑定成功后，**系统会自动在 mailcow 里建一条对应的中继记录**，并把这个域的出站切到该账号——你不需要手工改 postfix 配置。

> ⚠️ 新增账号后如果邮件发不出去，**先看 postfix 日志里到底是 `sent` 还是 `bounced`**。
> 本项目踩过一个坑：中继的 **SASL 用户名**写错（写成了带编号的形式而非服务商要求的固定值 `resend`），
> 会让该域**全部出站邮件被 `535 Invalid username` 拒投**，而且表面上只显示"没数据"，看不出原因。

### 5.4 怎么判断系统是否健康

打开 **管理员后台 → 域名总览**（页面上有"体检/检查"按钮），盯下面这几个指标。

| 指标 | 在哪看 | 健康标准 | 不健康说明什么 |
|---|---|---|---|
| **MX 是否指向本机** | 域名健康 / 域名列表 | 全部 = `mail.pony-it.com` | 指向别处 → 该域**收不到邮件**（入站故障） |
| **SPF** | 域名健康 | 存在 `v=spf1`、授权本机、以 `-all` 收尾 | 缺失/写错 → 认证 fail，投递率下降 |
| **DKIM** | 域名健康 | 公钥已发布、`p=` 的值非空、密钥长度 **≥ 2048 bit** | 查不到公钥 → 签名验不过 |
| **DMARC** | 域名健康 | 存在记录；越靠近 `p=quarantine`/`p=reject` 越好 | `p=none` 只监控，保护力有限 |
| **PTR（反向解析）** | 域名健康 | 与 `mail.pony-it.com` **一致** | 不一致 → 多数接收方扣分 |
| **出口 IP 黑名单** | 域名健康 | 未列入任何名单 | 列入 → 直接投递失败，需申请移除 |
| **网站可达性** | 域名健康 | 有可访问的 A 记录/网站 | 空壳域 → 收件方更容易当垃圾源 |
| **本机出站打分（rspamd）** | 域名健康 | 打分正常（**阈值 15.00**，越低越安全） | 分数高 → 本机也认为内容/行为可疑 |
| **域名信誉 / 举报率** | Google Postmaster Tools | 信誉 **High/Medium**；举报率 **< 0.10%** | 信誉 Low/Bad 或举报率超线 → 立即减量/停发 |
| **养号是否正常运行** | 域名总览 → 养号 | 「今日已运行」+ 发送量按计划递增 + 失败数为 0 | 「今日未运行」是要立刻发现的故障（可能配额为 0，也可能是调度器没跑） |

> **看趋势，不看单点。** 尤其是 Postmaster 的数据本身有 1–2 天延迟，且**发送量不足时会显示"暂无数据"——那是正常的，不是故障**。

### 5.5 后期怎么跟 AI 聊天让它帮忙"加号、加 Key"

你可以让 AI 助手帮你完成"加中继账号""绑定域名""体检排查"这类操作，但**你给它的上下文必须是安全的**。

#### ✅ 该提供的上下文（安全）

- **现象描述**：例如"某域发到 Gmail 进垃圾箱了""某个账号加不上，提示要 Full access""养号页面显示今日未运行"。
- **界面上的状态**：域名验证徽章（pending / verified / failed）、号池里"已用 / 上限"进度条、养号计划的"第 N/M 天"、Postmaster 的域名信誉档位。
- **脱敏后的 Key 形态**：例如 `re_xxxx…xxxx`——**只给掩码部分**。本项目界面默认也只显示掩码。
- **认证头原文**：`Authentication-Results` 那一行（它不含密钥）。
- **报错信息原文**：把界面或日志里的**报错文字**整段贴给它（本项目设计上，报错也不会包含密钥）。
- **命令输出**：`dig` 查 DNS 的结果、`docker compose ps` 的容器状态等。

#### ⛔ 绝不能给 AI 的（安全红线）

| 绝不能提供 | 原因 |
|---|---|
| **完整的中继 API Key**（未经脱敏） | 拿到即可冒用你的身份发信、管理域名 |
| **任何密码**（服务器、邮箱、数据库） | 直接危及账号安全 |
| **DKIM 私钥 / 任何私钥文件内容** | 泄露即可伪造你所有邮件 |
| **Cloudflare API Token** | 泄露即可被篡改你的 DNS |
| **`.env` / `mailcow.conf` 的原文** | 里面可能含明文数据库与系统密码 |

> 如果你**不小心**把密钥贴给了谁（包括 AI），**正确的补救是立刻到服务商后台把这把 Key / Token 吊销并重建**，而不是"希望它没被看到"。

## 六、术语表

| 术语 | 一句话解释 | 在哪能看到 |
|---|---|---|
| **发件信誉** | 收件方根据你过去发信历史偷偷给你打的分（涨得慢、掉得快） | Google Postmaster Tools；域名健康里的"域名信誉" |
| **SPF** | DNS 里的一条声明："只有这些机器能代表我发信"（身份证） | 域名健康 → SPF；`dig TXT <域>` |
| **DKIM** | 给邮件加的防伪签名，用 DNS 里的公钥验证（防伪章） | 域名健康 → DKIM；`dig TXT <selector>._domainkey.<域>` |
| **DKIM selector** | 签名用的"钥匙编号"，DNS 记录名必须和它对应 | 域名健康 → DKIM（会显示 selector 名） |
| **DMARC** | 规定"认证不过的信该怎么办"的策略（门规） | 域名健康 → DMARC；`dig TXT _dmarc.<域>` |
| **DNS** | 互联网的"电话簿"，登记域名相关的各种信息 | 你的 DNS 服务商（本项目用 Cloudflare） |
| **MX 记录** | 决定"发给这个域的邮件投到哪台服务器" | `dig MX <域>`；域名健康 → MX |
| **PTR / 反向解析** | 用 IP 反查域名的记录，应与邮件主机名一致 | `dig -x <IP>`；域名健康 → 反向解析 PTR |
| **黑名单 / RBL** | 一份"差评名单"，被列入会导致投递失败 | `dig <反过来的IP>.zen.spamhaus.org`；域名健康 → 黑名单 |
| **中继 / Relay** | 专业的"邮件转运公司"，用它自己的高信誉 IP 帮你发信 | 后台「中继号池」；服务商后台 |
| **号池** | 多个中继账号凑成的池子，突破"单账号限绑 3 个域"的限制 | 后台「中继号池」 |
| **relayhost** | mailcow 里"这个域出站走哪个中继"的设置项 | 域名总览 → "出站中继"列 |
| **养号 / Warmup** | 模仿正常人的收发节奏，慢慢累积域名信誉的自动化功能 | 后台 → 系统 → 养号 |
| **批量突发 / burst** | 短时间内集中、大量发信——本项目唯一被反复验证的触发因素 | 无需查看；靠控制发送节奏避免 |
| **进箱率** | 发出的邮件进入收件箱（而非垃圾箱）的比例 | 自己抽样；Postmaster 的间接数据 |
| **举报率 / Spam rate** | 收件人**主动点"举报垃圾邮件"**的比例（≠ 被判垃圾的比例） | Google Postmaster Tools；红线 0.30%，目标 < 0.10% |
| **硬退信** | 发到不存在/已废弃的地址，被对方直接退回 | 中继后台投递日志；目标 < 2% |
| **RDAP** | 域名的权威注册数据（"户口本"），用来查域名注册时间 | 命令行/在线 RDAP 查询 |
| **认证头 / Authentication-Results** | 收件方写在邮件头里的认证判定结果（最权威） | 邮件的原始头 |
| **MTA-STS** | 保护"别人发给你"的邮件的入站传输安全机制 | `dig TXT _mta-sts.<域>`；域名健康 |
| **rspamd** | 本项目本机的反垃圾打分引擎 | 域名健康 → 本机出站打分（阈值 15.00） |
| **opcache** | PHP 的代码缓存；本项目**改了 PHP 必须重启 php-fpm** 才生效 | 运维知识，非界面 |
| **Postmaster Tools** | Google 官方工具，唯一能看到 Gmail"怎么看你"的途径 | 后台 → 系统 → Postmaster Tools |

## 七、一页纸总结

1. **邮件进不进垃圾箱，是概率问题，不是配置开关。** 没有 100% 的方案。
2. **四层判定**：认证（身份证）/ 信誉（口碑）/ 内容（写了什么）/ 行为（怎么发的）。
3. **本项目实测最硬的事实**：Gmail 自己返回 `dkim=pass spf=pass dmarc=pass`，第三方 Port25 独立复核也全 pass，
   **邮件依然进垃圾箱**。所以"认证过了"不代表"能进收件箱"。
4. **真实主因**：新注册域的批量画像 + 中继出口 IP 的个体信誉 + **批量突发发送**。
5. **我们做对的**：补齐 SPF/DKIM/DMARC；改用中继搭高信誉 IP 的车；用号池隔离风险；用养号慢慢攒信誉。
6. **排查先分方向**：出站看"认证头"，入站先查"MX"。
7. **日常三件事**：盯 Postmaster 的**信誉分与举报率**；控制**发送节奏**（永不突发）；**关键操作与密钥永不外泄**。
8. **什么时候该找人**：当你已经确认"认证全过、DNS 全对、也没被拉黑"，却仍然进垃圾箱——
   这时候该做的**不是继续折腾配置**，而是（a）接入 Postmaster 看官方数据、（b）把重心放到"养信誉"、（c）找人复盘发送行为与收件人质量。
