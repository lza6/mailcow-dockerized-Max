# 中继方案实施指南

> 决策日期：2026-10-08
> 适用：mail.pony-it.com 及 16 个发件域
> 目标：解决「邮件进 Gmail 垃圾箱」问题
> 本方案不含任何密钥，可对外传阅。

---

## 一、为什么走中继（结论与依据）

### 实测得出的根本原因

| 测试项 | 结果 |
|---|---|
| 16 个域 SPF/DKIM/DMARC | **全部配置正确、全部验证通过** |
| 邮件是否成功投递到 Gmail | **成功**（对方返回 `250 OK`） |
| 最终落点 | **全部进垃圾箱**（16/16） |
| 连 152 天的老域 pony-it.com | **同样进垃圾箱** |
| 4 种不同内容变体 | **全部进垃圾箱** |
| 自建 IP 属性 | OVH 数据中心 IP，`hosting:true`，**零发信信誉** |

**结论：问题不在认证，在「发送 IP 的信誉」。**

### 为什么不自己建服务器发

| 尝试 | 结果 |
|---|---|
| 香港机器 103.233.252.213 | 25 端口**出站被封** |
| 美国机器 154.37.208.171 | 25 端口**出站被封**（实测 4 个 Google MX 全部超时） |
| 代理池 3920 条 | 仅 4 条能连，且 **SPF 对不上，比现在更糟** |
| 免费代理项目定位 | 那是给 HTTP 图片请求用的，**不适用于 SMTP** |

**关键事实**：SMTP 协议规定投递必须连对方 **25 端口**，这是协议层面的硬约束，无法通过改端口绕过。国内外主流云商 **90% 默认封 25 端口**。

**实测证据**（美国机器 postfix 日志）：

```
postfix/smtp: connect to gmail-smtp-in.l.google.com[74.125.197.27]:25: Connection timed out
postfix/smtp: connect to alt1.gmail-smtp-in.l.google.com[172.253.116.27]:25: Connection timed out
postfix/smtp: connect to alt2.gmail-smtp-in.l.google.com[192.178.223.27]:25: Connection timed out
postfix/smtp: connect to alt3.gmail-smtp-in.l.google.com[172.253.157.26]:25: Connection timed out
网络层状态：SYN-SENT → 包发出后无响应，被上游静默丢弃
```

### 中继如何解决

```
现状（直发）：
  你的服务器(OVH冷IP) ----25端口----> Gmail        ❌ 25被封 / 进了也进垃圾箱

中继方案：
  你的服务器 ----587端口----> 中继商(高信誉IP池) ----25端口----> Gmail   ✅
                              ↑
                        587 端口所有云商都开放
```

**中继把「IP 出身差 + 25 被封」两个问题一次解决。**

## 二、中继方案优缺点（务必了解）

### 优点

| # | 优点 |
|---|---|
| 1 | **立刻可用** —— 无需养 IP 信誉，无需等 1-3 个月 |
| 2 | **绕开 25 端口封锁** —— 只用到 587，所有机器都通 |
| 3 | **专业 IP 池** —— 中继商的 IP 有多年积累的发信信誉 |
| 4 | **自动处理退信/投诉** —— 中继商会反馈 bounce 和 complaint 数据 |
| 5 | **有投递统计** —— 可看到送达率、打开率、退信率 |
| 6 | **成本可控** —— 最低约 $0.10/千封（Amazon SES） |

### 缺点（必须接受）

| # | 缺点 | 严重度 | 缓解方式 |
|---|---|---|---|
| 1 | **不满足「源头完全自控」** —— 邮件内容与收发元数据经过第三方 | 高 | 选信誉好的大厂，签数据处理协议 |
| 2 | **有额度上限** —— 超额需付费或被限速 | 中 | 按实际量选套餐 |
| 3 | **必须改 DNS（SPF）** —— 改错会直接导致 `spf=fail`，比现状更糟 | **高** | 改动前完整备份，可一键回滚 |
| 4 | **供应商风险** —— 可能涨价、关停、改政策 | 中 | 不把长期方案押在免费额度上 |
| 5 | **内容可能被审核** —— 部分中继商扫描/限制内容 | 中 | 选明确的商业条款 |
| 6 | **多一层故障点** —— 中继挂了就完全发不出信 | 中 | 可配置备选中继 |
| 7 | **免费额度有限** —— Resend 3000 封/月、Mailgun 100 封/天 | 中 | 长期转 Amazon SES |

### 关于「稳定率」的实话

**业内没有公开的「稳定率」指标。** 真正需要看的是三个东西：

| 指标 | 含义 | 可否查到 |
|---|---|---|
| **基础设施可用率 (SLA)** | 服务商服务器不宕机的保证 | ✅ SES 99.9%、Resend 企业版 99.99% |
| **进箱率 (Inbox Placement)** | 邮件进收件箱的比例 | ❌ **服务商不公开**，取决于你的发件人信誉 |
| **限速 (Rate Limit)** | 每秒/每天发送上限 | ✅ 文档有 |

**影响进箱率波动的真实因素：**

1. **共享 IP 池会被其他客户影响** —— 同池若有人群发垃圾，整池信誉下降
2. **新域名在中继上仍是新域名** —— 中继不会给你的域名「加分」
3. **发送量突增会触发风控** —— 即使用中继也一样

**重要认知**：发信量低时，**共享 IP 优于独立 IP**（共享池已有积累）；发信量高时才需要独立 IP。因此**不要**在起步阶段购买独立 IP。

## 四、实施步骤

### 第 0 步：准备工作（我方已完成）

- [x] 16 个域 DNS 全量备份（23 个 zone / 172 条记录，含记录 ID）
- [x] Cloudflare API 接入验证通过（可批量读写 DNS）
- [x] 一键回滚脚本就绪
- [x] 现有 mailcow 中继条目已盘点

### 第 1 步：你在 Resend 后台添加域名 ⬅ **当前卡在这里，需要你操作**

1. 打开 <https://resend.com/domains>
2. 点击 **Add Domain**
3. 输入域名：`urbansproutglobal.com`（**建议先只加这一个，验证通过再推广**）
4. Region 选择默认（US East）即可
5. 可选设置保持默认（不开追踪、不用自定义 Return-Path 子域，减少出错面）
6. 提交后 Resend 会显示一组 DNS 记录（通常 3–4 条，含 SPF / DKIM / MX）
7. **把这一屏截图或复制文本发给实施方**

**Resend 会给出的记录类型**（具体值由 Resend 针对你的域动态生成，以后台显示为准）：

| 类型 | 名称（示例） | 用途 |
|---|---|---|
| TXT | `send.urbansproutglobal.com` 或根域 | SPF（`include:amazonses.com`） |
| TXT | `resend._domainkey.urbansproutglobal.com` | DKIM 公钥 |
| MX | `send.urbansproutglobal.com` | Return-Path 回信地址 |

> ⚠️ **注意**：Resend 的 DKIM 私钥由 Resend 持有并签名。这意味着**邮件签名密钥在第三方手里**——这是中继模式的固有代价。

### 第 2 步：写入 DNS（我方自动执行）

收到记录后，我方将：

1. 用 Cloudflare API 读取当前记录并**再次备份**
2. 写入 Resend 要求的记录
3. **替换（不是追加）原 SPF 记录**
   - ⚠️ **关键**：一个域名只能有一条 SPF 记录。两条 SPF 会直接导致 `spf=permerror`，比现状更糟
   - 正确做法：把 `include:amazonses.com` 合并进原 SPF，例如：
     ```
     原：v=spf1 mx a:mail.pony-it.com -all
     新：v=spf1 mx a:mail.pony-it.com include:amazonses.com -all
     ```
4. 等待 DNS 生效（TTL 300 秒，通常 5–30 分钟）

### 第 3 步：在 Resend 后台点击验证

DNS 生效后回到 Resend 后台点 **Verify**，状态变为 `Verified` 即可。

### 第 4 步：配置 mailcow 中继（我方自动执行）

mailcow 中已有中继条目（`smtp.resend.com:587`），执行以下操作：

1. 在 **管理员后台 → 配置 → 路由（Routing）** 中确认 Resend 中继条目
2. 在 **域名编辑页** 把 `urbansproutglobal.com` 的中继绑定到 Resend 条目
   - 或修改数据库 `domain.relayhost` 字段
3. 确认 postfix 出站走中继

### 第 5 步：发测试信验证（我方执行）

1. 从 `daniel@urbansproutglobal.com` 发一封到测试 Gmail
2. 通过 IMAP 读取落点（收件箱 / 垃圾箱）
3. 提取 `Authentication-Results` 头，确认 SPF/DKIM/DMARC 状态
4. **把结果反馈给你**

### 第 6 步：看结果决定后续

| 结果 | 说明 | 后续 |
|---|---|---|
| ✅ 进收件箱 | 证实「IP 出身」是主因，中继有效 | 推广到其余 15 个域；长期转 Amazon SES |
| ⚠️ 仍进垃圾箱 | 说明域名年龄/发送行为是主因 | 需同步做：集中 1-2 个主域、控制量、给主域建站 |
| ❌ 验证失败 | DNS 或配置问题 | 用备份回滚，排查后重试 |

## 七、后续可选的加强措施（配合中继一起做效果更好）

中继解决「IP 信誉」，但以下三项能进一步提升进箱率：

| # | 措施 | 效果 | 说明 |
|---|---|---|---|
| 1 | **集中到 1–2 个主域发信** | ⭐⭐ | 16 个新域同时发信是典型垃圾特征 |
| 2 | **给主域建真实网站** | ⭐⭐ | `urbansproutglobal.com` 当前连 A 记录都没有，Gmail 会检查域名是否有真实内容 |
| 3 | **加 `List-Unsubscribe` 头** | ⭐ | 收件箱内 60 封正常邮件 **100%** 都有此头 |
| 4 | **配置 Google Postmaster Tools** | 数据支撑 | 可看到 Google 官方给出的域名信誉评分与垃圾箱率 |
| 5 | **控制发送节奏** | ⭐⭐ | 新域前 30 天建议每天不超过 20–50 封 |

## 八、一句话总结

> 邮件认证没有问题，问题是**发送 IP 没有信誉、且 25 端口被封**。
> 中继用它的高信誉 IP 池 + 开放的 587 端口，一次性绕开这两个障碍。
> 代价是**失去部分源头控制权**（内容和签名密钥经过第三方），以及**成本或额度限制**。
> 推荐路径：**Resend 免费额度验证效果 → 确认有效后转 Amazon SES 长期使用**。
